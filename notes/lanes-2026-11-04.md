# Lanes: many instances in one vector (2026-11-04)

A design note, with its measurement first. It follows the graph report
(notes/graph-2026-11-02.md): half the corpus's work is in repeated
instances (`sum`, `each`), a quarter of it in voices threads can't help,
and 88% of the instance work is plain arithmetic.

## The design

`sum(N, k => body)` today is N copies of the body, unrolled, each with
its own regions one after another (instance-major). `poly`'s voices are
already a C loop over instances (emit_voice_loop), with each voice's
regions a span apart, and what depends on the voice hoisted into arrays
filled once a block.

Lanes would make every qualifying sum a loop over k too, and lay the
state out lane-major: field e of the body's region i, for instance k, at
`base_i + e * N + k`. The loop's body is then the same scalar code over
rows, which a vectorizing compiler turns into vectors of 2 (NEON), 4
(AVX2) or 8 (AVX-512) instances. Each instance's term goes into a row,
and the row is added after the loop in the order the unrolled sum adds
it, instance 1 first, so the bits stay those of the unrolled sum: IEEE
arithmetic is the same in every lane, and only the sum's order could
differ. A body that calls a native (a filter, a delay) or a libm sine
stays a scalar loop: one call a lane, the rest in vectors where the
compiler can.

What it would take: state accesses emitted as region and element (not
`offset + e` in the text), so the layout can change; the hoisted
per-instance values as rows (the voice loop's arrays); the lazy first
values settled before the loop (below); and `-O3` or the dynamic cost
model for the -O2 build, since `-O2`'s cheap model vectorized nothing.

## Measured on the uConsole's A72: no gain

Two kernels in the shape codegen writes (notes/lanes/), each run as
today and as lanes, 64 instances, 10 s of sound, bit-identical every
time:

| kernel | as today | lanes | gain |
|---|---|---|---|
| partials.c: 64 turned partials (the turner's step, an amplitude each) | 0.34 s | 0.29 s | 1.15x |
| resonators.c: 64 driven `dho` (waterfall's bank) | 0.36 s | 0.38-0.41 s | 0.9-1.07x |

And partials.c's 1.15x isn't the vectors: checking each partial's
first-value flag once a block instead of every sample, everything else
as today, gives the same 0.29 s. On the A72 a vector holds two doubles
and its scalar code already keeps both floating-point pipes busy; the
resonators also divide, and a vector divide is no faster a lane.

So lanes don't pay on the uConsole. On a laptop's AVX2 (four doubles)
or AVX-512 (eight) they may; that is the open measurement:

    cc -O3 -march=native -ffp-contract=off -o /tmp/partials notes/lanes/partials.c -lm && /tmp/partials
    cc -O3 -march=native -ffp-contract=off -o /tmp/resonators notes/lanes/resonators.c -lm && /tmp/resonators

Below about 1.5x there, lanes aren't worth what they cost to build
(the state's layout is what hot-swaps match, and every native would
want a lane form).

## What the measurement found instead

Every `$state` in a def checks a flag every sample, to give it its
first value the first time its code runs (`if (s->pool[pf] == 0.0)`):
64 checks a sample in waterfall, one per `dho`. When the first value is
a constant (`$z = [0, 0]`, as `dho` and most filters write it), the
check can run once a block instead (hoist_init), before any sample: the
state holds the same value before its first use either way, so the bits
can't change. A first value made of the sample's signals keeps its
check. partials.c measures that at 1.17x on its own; it applies to
every voice with def state, laptop and uConsole alike.

**Done, and smaller in real patches** (codegen's nkVar: a first value
that compiles to a number, outside a loop of voices, is settled in
hoist_init). Seconds per 10 s of sound, blocks, one thread:

| patch | TCC before → after | -O2 before → after |
|---|---|---|
| waterfall (64 dho) | 6.53 → 5.93 | 0.69 → 0.69 |
| bowl | 2.58 → 2.60 | 1.22 → 1.20 |
| bush_doof_e | 19.9 → 19.0 | 9.29 → 9.29 |

TCC gains up to a tenth; gcc's -O2 already kept the check out of the
way (predicted, its stores off the hot path), which the small kernel
didn't show. A kernel overstates: measure in patches.
