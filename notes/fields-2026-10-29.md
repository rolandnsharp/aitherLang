# Fields of phasors: which way is aither's

**Status: decided and built (2026-10-29): A.** Arrays' elements are what their initial value is, so a state array holds phasors; the medium's law is a def, the step is `each`. B was rejected: `each` already is the local law, so `field` would be a second way to say it. COMPOSING has the ladder.
`patches/phasor_ring.aither` is the case: twelve phase oscillators in a
ring, each pulled toward its two neighbours. It runs today, but each
phasor lives split across two number arrays, its first side and its
second. The question is how a field of phasors should read in aither.

The test, from MANIFESTO.md: signals as field values, state as field
configuration, **evolution as a local update rule**, observation as
projection, coupling as shared field access. And PHILOSOPHY.md's: every
primitive earns its place against what the existing ones already say.

## The ladder: most fields need no new feature

Before any design, what physics already reads well, because the kind of
field decides it:

| the field | what writes it in aither today | needs state per place? |
|---|---|---|
| a linear medium driven at its modes (a plate, a drum, a room's resonances) | a sum of its modes: `sum(N, n => dho(drive * shape(n, x), f(n), d))` (demos/chladni) | no |
| a linear medium carrying waves (a string, a tube, a room's echoes) | travelling waves as delays (d'Alembert: f(x - ct) + g(x + ct)), a waveguide | no, delays are the field |
| oscillators all coupled to all (Kuramoto's own model, a bridge, a soundboard) | one shared cell, the mean field, every copy reading and writing it (sympathy.aither's `$board`) | no: one cell |
| polyphase, rotating fields | turns of one phasor (three_phase.aither) | no |
| **oscillators coupled to their neighbours, nonlinear** (the ring, a lattice, a complex wave on tv, reaction-diffusion) | a stored field: one value per place, stepped by a local rule | **yes** |

So the gap is only the last row: nonlinear, local coupling. It is real
(lattice physics, coupled-oscillator computing, synchronisation waves,
anything on tv that is a field rather than a picture), but it is one
row. Linear fields and global coupling should be written the functional
way, and COMPOSING should say so.

**Kuramoto all-to-all, today, no arrays:**

```
$mean = [0, 0]                                   # the field's mean, as the oscillators left it
let ring = sum(12, k =>
  $z = [1, 0]
  let moved = turn($z, step(k)) + $mean * couple
  $z = moved / amplitude(moved)
  $z)
$mean = ring / 12
```

## For the last row: three ways

### A. Arrays of phasors (data)

`$z = array(n, [1, 0])`: the initial value decides the element's shape,
as `$z = [0, 0]` already makes pair state. `$z[i]` is a pair.

```
$z = array(12, [1, 0])
each(12, i =>
  let moved = turn($z[i], step(i)) + ($z[(i + 11) mod 12] + $z[(i + 1) mod 12] - $z[i] * 2) * couple
  $z[i] = moved / amplitude(moved))
```

- For: the smallest change (one rule about an array's element), any
  topology (ring, line, grid, a graph by table), works with `each`,
  stepped arrays and tv's `pixel_index` as they are.
- Against: it reads as a data structure with index arithmetic (`(i + 11)
  mod 12`); the law of the medium is buried in subscripts.

### B. A field and its local law

The field is declared with its law: how each place's next value follows
from its value and its neighbours', all read as they were. Reading it at
a place is `$ring[k]`.

```
$ring = field(12, [1, 0], (z, near, k) =>
  let moved = turn(z, step(k)) + (near(-1) + near(1) - z * 2) * couple
  moved / amplitude(moved))

sum(12, k => pan($ring[k - 1][0] * 0.09, (k - 1) / 11 * 1.6 - 0.8))
```

- `near(d)` is the place d along; on a grid, `field([w, h], …)` and
  `near(dx, dy)`. Edges are part of the declaration: a ring or torus
  wraps (the default), `edge = [0, 0]` makes a medium that ends in
  nothing, which is how a string with fixed ends or a membrane with a
  clamped rim is said.
- For: it is the manifesto's sentence as code. The state is the field
  configuration, the evolution is a local rule, and no index arithmetic
  appears: a Laplacian is `near(-1) + near(1) - z * 2`, as physics writes
  it. One step for every place at once, so order never matters (it is
  `each` with held-back stores, which aither already has, made the only
  way to say it).
- Against: a new construct, and its design decisions (dimensions,
  neighbourhood, edges) become the language's. It needs A's pair
  elements underneath anyway.

### C. Coupling as delayed reading between copies

Let a `sum` copy read another copy's last value by its index:
`sum(12, k => … neighbour(k - 1) …)`.

- Against: copies are space and own their state, which is what makes
  `sum` simple; letting them name each other turns `sum` into an array
  with a hidden layout. Rejected.

## Recommendation (first draft; superseded by the status above)

**B, built on A.** Pair elements (A) go in first, because every stored
field needs them and they are a small, clean rule. `field` (B) is then
how a field is written: the law of the medium, not a loop over a data
structure. `each` and indexed stores stay for what isn't a field (a
scale being rewritten, a history). COMPOSING gets the ladder above, so
linear fields and global coupling keep being written as sums and shared
cells, which they should be.

Open for B: whether `near` is a function argument (as above) or the rule
takes a fixed set of neighbours `(z, left, right)`; whether `field` steps
every sample or `every = M` (tv: once a frame), as stepped arrays do.
