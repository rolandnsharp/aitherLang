# The voices of `poly` as one loop in the C

**Status (2026-10-30): built, the same day; see "Built" at the end.** Part
of the speed round for heavy physics audio on battery
([perf-2026-10-30.md](perf-2026-10-30.md)). Nothing in the language
changes: `sum` stays a fold and `poly` a sum of voices. Only the C the
compiler writes would change. TCC and the background `cc -O2` build
compile the same C (the -O2 build takes the source the voice loaded
with), so both would get the loop. Roland asked whether
loops go against aither being functional by design. In the language they
would. In the C they don't: aither already compiles `def rec`, its
recursion, to a C `for (;;)`, and a patch can't tell how the C is laid
out.

## The problem, measured (battery: four A53s at 1.0 GHz)

After a `send`, a voice plays on TCC until its `cc -O2` build lands. For
every heavy patch TCC is too slow (1.3 to 7.3 times real time), so it
drops out until then. The wait is gcc's compile time, and that follows
the size of the generated C.

48 s and `additive_swarm` from 316 KB and 53 s.)

`-O1` is not the way out: on `chord` it compiles in 9.4 s against 19.9
s (`-O2`, on an A53 with nothing else running) but runs 1.8 times slower
(0.46 against 0.26). It could be a middle tier (TCC, then `-O1`, then
`-O2`), halving the wait, but it doesn't touch the cause.

## Why the C is that big

`midi_keyboard` is `poly(8, voice)`: a `sum` of 8 voices, each the
caller's lambda inlined with its slot number. The compiler unrolls every
`sum`, so the C holds the voice 8 times, differing only in the slot
(1–8) it reads. `chimera`'s voice is about 44 partials, each a phasor,
a drifting sine and its arithmetic: 77 KB of C, eight times over.

## The design: the voices as a loop, everything inside as now

A `sum` whose body doesn't need its index known at compile time is
written as a C loop over the index; otherwise it unrolls
as now. In practice the target is `poly`'s sum of voices: the index only
picks a slot (`midi_voice_freq(n)` and the rest take it at run time).
The `sum`s inside a voice still unroll, so their partial numbers stay
compile-time numbers and keep folding.

What the loop has to keep:

- **Each voice its own state.** Today each unrolled copy claims its own
  slots in the pool. In the loop the body claims one voice's slots, of
  span S, and voice k's are at base + k S. TCC and -O2 compile the same
  C, so their layouts agree by construction (the swap already checks
  the size). A hot swap from the unrolled C of before to the looped C
  should carry each voice's state over as well. How a swap matches
  state to the new layout (voice.c) has to be read before building; at
  worst a voice's state starts fresh once, on the first send after the
  compiler changes.
- **Per-block constants per voice.** A partial's turn (cos and sin of its
  step) is hoisted, computed once a block; in a voice it depends on that
  voice's frequency, so it becomes a small array filled once a block, one
  entry a voice.
- **Each voice its own noise.** `noise()` is seeded by where the call is;
  each voice's copy is a different place today. In the loop the seeds are
  an array, the same seeds as the unrolled copies get.
- **The same bits.** The voices are added in the same order, voice 1
  first (so 0.0 is never added to a first term and a negative zero
  survives). A voice whose slot has no note is 0 today by an `if` at run
  time, and stays so.
- **What can't loop.** A body that needs its index at compile time (an
  array size, a nested count, a table whose length it picks) unrolls.
  The compiler tries the loop and falls back.

The check is the corpus: every patch bit-identical, on TCC and -O2, plus
`make exact`, plus a state-layout check that TCC's offsets and the
loop's agree.

## What it should give

C about 8 times smaller for the keyboard patches (`chimera` from 619 KB
to perhaps 90 KB), gcc's time down with it, so a send's dropout shrinks
from minutes to seconds. Run time about the same: the same work, with
one voice's code hot in the cache instead of eight copies of it. Not
measured until built.

It doesn't make a patch that needs three A53s fit on one
(`chimera`, `tesla_jam`, `bush_doof_e`). That is multicore by instrument
([multicore-2026-10-18.md](multicore-2026-10-18.md)).

## Order

1. The loop for `poly`'s voices, with the bit-identity checks. Measure
   C size, gcc time, and run time on TCC and -O2 (TCC's may change
   either way: one copy of the voice in cache, but the slot no longer a
   constant).
2. If gcc is still slow on patches without `poly` (`bush_doof_e`,
   `tesla_jam`, `didge_scope`), look at what fills their C next.
3. `-O1` as a middle tier, only if 1 and 2 leave a wait worth halving.

## Built (2026-10-30)

As designed, with one addition: the clock turner (a sine of `t`, the
drift in `chimera`, `cello_max` and others) loops too, its per-block
check (has the rate moved) one a voice. A sum loops when its index is
read only as a voice slot (`midi_voice_freq(n)` and the rest), which is
`poly`'s. Every patch is bit-identical to the unrolled C, on TCC and
-O2 (each keyboard patch checked against `AITHER_LOOP=0` with the
three-chord script, and the whole corpus); all 61 test suites pass.
