# scope and tv: two displays for the pair

Decided 2026-10-16 (Roland, with Claude on the uConsole). How aither's
output is seen: two small programs that read the pair stream, one as
a vector display and one as a raster display, and how sound and
visuals are live-coded side by side. Builds on
[pair-output-2026-10-15.md](pair-output-2026-10-15.md). Nothing here
is built yet.

## The decision

```
aither sound.aither | play | scope | aither visuals.aither | tv
```

- **`scope`** is a vector display, an oscilloscope: each pair is a
  point, the beam joins the points, the phosphor fades them.
- **`tv`** is a raster display, a television: samples fill pixels in
  raster order, frame after frame, and each pixel's pair is a complex
  number shown by domain colouring.
- **Both are filters.** Float pairs in on stdin, the same bytes out on
  stdout, drawing in a window of their own (SDL3 and OpenGL ES 3, see
  "Drawing"). `play` becomes a filter too, so a chain can be heard and
  seen at once.
- **Two engines, both live-coded:** the sound engine you play, and a
  visuals engine whose `input()` is the music and whose output is the
  picture.
- **Neither display has effects, modes or presets.** Everything that
  moves is aither code. The displays only decide how a pair becomes
  light.

Nothing changes in the language. The stdlib gains two pixel helpers;
the engine may gain one input option (open question 1).

## Displays are readers

As in the pair-output note, the numbers mean what the program reading
them says they mean. A display is fully defined by three answers:

| | grouping | a pair is | memory between frames |
|---|---|---|---|
| `scope` | none: a stream of points | a point (x, y) | fading phosphor |
| `tv` | frames of w×h samples | one pixel, a complex number | none |

Other readings are possible (a turtle's steps, a swarm of particles,
the mesh warp under "Superseded"). Each would be another small
program of the same family, never a mode of these two.

## scope

- Reads interleaved float32 pairs. A pair is a point: x and y in
  −1..1, y up, square.
- The beam draws a line from each point to the next with the same
  energy per sample, so where it lingers is bright and where it moves
  fast is faint. Brightness is dwell, as on a tube.
- Outside −1..1 nothing is drawn, nor the segment to or from that
  point: a jump off screen blanks the beam (SCOPE.md's convention).
- The phosphor decays every frame. Its constants, the six palettes
  (green, amber, cyan, blue, white, red) and the CRT boot and shutdown
  come from the Nim terminal-oscilloscope it replaces.
- No Y-T mode and no trigger. A time base is a patch's last line
  (SCOPE.md, "A waveform that holds still"). The music piped straight
  in shows left against right: the vector scope of the mix.
- Flags: the palette and the decay. Nothing else.

## tv

- Reads interleaved float32 pairs. A frame is w×h samples
  (`--size WxH`) in raster order: rows top to bottom, each row left to
  right. The frame rate is the stream's rate divided by w×h: whatever
  the stream delivers.
- A pair is one pixel's complex value w, shown by domain colouring:
  hue from its phase, brightness from its magnitude, black at 0 and
  full at |w| ≥ 1.
- A frame is shown once it is complete (double-buffered, so no
  tearing) and scaled to the window, crisp or soft.
- No memory. Persistence, feedback and trails are state arrays in the
  patch.
- It counts samples from the first byte it reads. The patch and tv
  must agree on the size; a mismatch shears the picture (every row
  starts in the wrong place), which is the one way to get it wrong.

## The pixel helpers

A visuals patch needs to know which pixel the current sample is:

- `pixel(w, h)`: the pixel's centre as a pair, x across −1..1, y up,
  square pixels, so y spans ±h/w (±0.75 for 160×120).
- `pixel_index(w, h)`: its raster index, 0 .. w·h − 1, for state
  arrays.

Both are derived from the engine clock (rounded, allowing for the
clock's first sample), not from a counter in the voice, so a hot swap
or a newly sent voice lands on the same grid tv is counting. Names to
be confirmed when built.

## What the visuals engine does

Everything that moves:

- **Fractals as systems you watch run.** Mandelbrot is the map
  z → z² + c applied over and over. Keep one z per pixel in a state
  array, advance it one step per frame, and the fractal grows on
  screen. A sketch, to be checked against the language when tv is
  built:

  ```
  let k = pixel_index(160, 120)
  let c = pixel(160, 120) * 1.5 - [0.5, 0]   # centre -0.5, half-width 1.5
  $z = array(2 * 160 * 120)                  # one complex z per pixel, kept between frames
  let z = [$z[2 * k], $z[2 * k + 1]]
  let next = if magnitude(z) > 2 then z else cmul(z, z) + c   # escaped points stay where they left
  $z[2 * k] = next[0]
  $z[2 * k + 1] = next[1]
  next / (1 + magnitude(next))               # into the unit disk, phase kept
  ```

- **Morphing one map into another:** blend `c` toward a fixed
  constant over a minute and Mandelbrot becomes a Julia set. Julia,
  Burning Ship and Newton fractals are a one-line change.
- **The MilkDrop look:** keep the previous image in a state array and
  set each pixel to the old image read at a warped position: zoom,
  spin, the kaleidoscope fold, a liquid wobble, all functions of the
  pixel position and driven by the music.
- **A beam plotted into the image:** the patch writes its trace into
  the state array as it goes.
- **Reacting to the music:** `input()` is the mix. Envelope followers,
  onset detection and pitch tracking are aither code.
- **Fields whose points talk to their neighbours:** reaction-diffusion,
  the Game of Life, waves on a grid: the same pattern, reading the
  state array at the next pixel.

## Two engines

- Separate sockets: `AITHER_SOCK=/tmp/aither-vis.sock aither
  visuals.aither`, and an alias (`vis send visuals.aither`) for the
  second one.
- What it buys: isolation (a broken visuals patch can't silence the
  music), a core each, sync for free (the visuals engine is clocked by
  the pipe), one language and one codebase.
- Both engines can subscribe to the same MIDI port, so the gamepad can
  steer the visuals as well as the sound.
- The trade-off, accepted for the separation: the visuals see only the
  mix, not the sound engine's names (its `f0`, bar phase, lip
  pressure). A VJ watches the music, not the musician's patch. When a
  piece needs the exact coupling, the trace goes in the sound patch
  (SCOPE.md) and the two are rendered separately.

## Who sets the pace

- `play` is the clock: the sound card drains it in real time and
  everything upstream follows.
- `play` passes on its input unchanged (not the clamped copy it sends
  to the card) and never blocks on it. If a display downstream falls
  behind, `play` drops blocks to it rather than stall the sound: a
  10 ms gap in what the visuals hear, never in what you hear.
- The displays read greedily. `scope` plots every point it receives;
  `tv` shows the newest complete frame at each screen refresh.
- Without `play` in the chain (`aither trace.aither | scope`, a
  free-running visuals engine), a display paces its reading to the
  nominal rate, so the patch runs in real time rather than as fast as
  the CPU allows.
- The visuals engine is paced by its input: one sample out per sample
  in. That ties tv's size to the music's rate.

## Rates and sizes

With the music on stdin at 48 kHz, the visuals engine makes 48 000
pixels a second:

| tv size | frames per second at 48 kHz |
|---|---|
| 32×24 | 62.5 |
| 64×48 | 15.6 |
| 160×120 | 2.5 |

A free-running visuals engine (nothing on stdin) can run at any
`AITHER_RATE`: 160×120 at 60 fps is 1.152 MHz. Feeding the music into
an engine at that rate needs it to hold each input frame for several
output samples (open question 1).

Cost, estimated from this week's measurements: at 1.152 MHz the
engine's own per-sample floor is about 7 % of an A72 core and 19 % of
an A53, and a lean visuals patch adds perhaps 15–40 % of an A72. To be
measured when built. Long delays and reverbs don't fit the pool at
MHz rates (`bush_doof_e` already fails at 480 kHz).

## What a visuals patch must respect

The engine guards the stream as if it were sound:

- A NaN or infinity resets the voice's pool, which wipes its state
  arrays: a fractal restarts. Keep iterations bounded (the sketch
  freezes escaped points).
- Within 20 s of a send, a sample above 3.0 rolls the voice back to
  the previous version; above 8.0 at any time mutes it as a runaway.
- So outputs stay within ±1, which both displays' conventions ask for
  anyway.

## Drawing: SDL3 and OpenGL ES 3

Decided the same day, after the first draft of this note: elegance,
and the GPU whenever there is one. Dependencies are fine.

- **SDL3** opens the window, makes the GL context and reads the keys:
  a Wayland window under river, an X11 one elsewhere, or full screen
  with no desktop at all (KMSDRM), for a projector on the HDMI port.
  On this system SDL2 is only a compatibility layer over SDL3
  (`sdl2-compat`), so SDL3 directly: one package, `sdl3`.
- **OpenGL ES 3** does the drawing. The uConsole's GPU is a Mali-T860
  under Mesa's panfrost (checked): OpenGL ES, and no Vulkan driver
  installed (Mesa's Vulkan driver for Mali covers newer generations).
  That rules out SDL3's own GPU API, which needs Vulkan, Metal or
  Direct3D 12.

How each display draws:

- **scope:** each frame's points go up as one line strip. Every
  segment is a soft-edged quad whose brightness is its duration over
  its length, so the beam is bright where it lingers: dwell, the
  physics, not an effect. The segments add up in a float buffer; each
  frame one pass fades it by the decay, two blur passes make the
  bloom, and a small shader maps intensity to the palette.
- **tv:** each frame goes up as a texture of complex values, two
  floats per pixel. Domain colouring is a short fragment shader;
  crisp or smooth scaling is the texture's filter.
- The CPU stays free for the two engines, which on the uConsole is
  where it is needed.

Without a GPU, the same GL code runs on Mesa's software rasteriser
(llvmpipe), headless on lab for instance. There is no second,
CPU-only renderer to maintain.

One renderer, three destinations for the finished frame:

- the window;
- the terminal: the frame read back and printed as characters
  (Braille or half-blocks), for ssh. This replaces the separate
  terminal renderer the Nim scope has;
- raw frames for `ffmpeg`, for the stream: on an output of their own
  (a path or a FIFO), since stdout carries the pass-through.

To check first, on the T860:

- **The phosphor buffer needs more than 8 bits per channel.** At 8 bits
  a dim trail fading by 0.85 a frame rounds back up and never quite
  disappears. Confirm panfrost can render to half-float buffers
  (`EXT_color_buffer_half_float`); if it can't, an 8-bit buffer with a
  dithered fade.
- **The GLES version panfrost exposes,** and half-float textures for
  tv (filterable in GLES 3.0, which smooth scaling needs).

## Superseded and rejected

- **`mill`**, a mesh-warp display (the first 768 pairs of each frame
  set where a 32×24 mesh samples the previous frame, the rest are a
  beam drawn on top): shelved. tv contains it in meaning, since the
  warp is a state-array read at a warped position. mill would win on
  cost and resolution (full screen from a 48 kHz stream). Build it
  only if tv's resolution or battery cost disappoints on the uConsole.
- **The image loop**, a per-pixel backend of the compiler (GLSL or
  C): not needed. tv is the image loop, done by the sample rate.
- **Effects in the display** (`osc --warp`, an effect chain with
  presets, the `.paint` scenes as presets): rejected. The displays have
  no opinions.
- **N-channel outputs and an `out` keyword:** still rejected. The pair
  is enough for both displays.
- **The name `osc`:** collides with the stdlib's `osc(shape, freq)` and
  with Open Sound Control. `scope` was free: the meters verb that had
  it is `levels` since 2026-10-15.
- **Talking Wayland directly:** workable with no new packages (the
  client library, its headers, wayland-scanner and `xdg-shell.xml` are
  installed), but about 250 lines of window plumbing, Wayland only,
  and scaling on the CPU. SDL3 instead.
- **SDL3's GPU API:** needs Vulkan, Metal or Direct3D 12; the T860
  has OpenGL ES only.
- **A separate terminal renderer:** replaced by reading back the GL
  frame.
- **Passages this note supersedes**, to be updated when scope is
  built: SCOPE.md's "The layer on top" and its "a session is heard or
  seen, not both"; the pair-output note's "Sound, picture and radio
  are not simultaneous" and its visualiser paragraph. Pass-through
  filters make a session heard and seen together.

## Open questions

1. **The engine's input rate.** An option giving stdin's rate (say
   `AITHER_IN_RATE`) so the engine holds each input frame for
   rate ÷ in-rate output samples: a music-reactive tv bigger than
   32×24 at 60 fps. It is the one engine addition this design asks
   for. Without it: small pictures, or visuals that don't hear the
   music.
2. **tv's default size.** 64×48 is 15.6 fps at 48 kHz.
3. **Where the code lives.** In aitherLang beside `play` and `pad`
   (`tools/scope.c`, `tools/tv.c`, a shared `tools/display.h` with the
   stdin reader, pass-through, pacing, the SDL3 and GL setup, the three
   destinations and the palettes), or in a repo of their own like
   terminal-oscilloscope.
4. **Colour.** The hue wheel's orientation and the brightness curve
   for domain colouring.
5. **The engine at MHz rates.** The per-sample work still done in Nim
   (voice stats, the ring buffer) shows at these rates. The "stats into
   C" item from 2026-10-15 earns its place.
