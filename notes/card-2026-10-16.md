# card: one clock for output and input

**Status: built 2026-10-17** (`tools/card.c`). Discussed 2026-10-16
(Roland, with Claude). Reviewed by the session that built `scope` and `tv`; its three
fixes are rules 1–3 below, recorded at Roland's request. No engine
change. Comes out of the active-sensing ideas in
[sensing-2026-10-16.md](sensing-2026-10-16.md): lock-in detection, the
cable tracer, sweep analysis and the metal detector all send a signal
out and read it back, so they need a known, fixed loop delay.

**The engine is already lockstep.** `pumpPipe` reads a block, mixes it
and writes it, so output sample n is computed from input sample n. The
unknown is outside the engine. Out of the DAC, through the world, into
the ADC, then `arecord`, a pipe, aither, a pipe and `aplay`: two pipes
of up to about 170 ms each, filled to however much the start order
left. That delay is arbitrary on every run, fixed while it runs (if
both directions are on one card), and moved silently by an xrun. That
breaks lock-in, sweep analysis and the metal detector.

**`card`** opens capture and playback on one ALSA device, links them
(`snd_pcm_link`) so they start on the same frame, and runs a command
with its stdin and stdout connected:

```
tools/card -- aither lockin.aither
tools/card -- sh -c 'aither lockin.aither | scope'    # a display inside the loop
```

Each period: read from the ADC, write to the child, read one block
back, write to the DAC. Because the engine is lockstep, the pipes never
hold more than one block, so the round-trip delay is fixed: the
silence `card` primes playback with, plus the converters. You measure
it once per card with a cable from out to in and write it into the
patch, in seconds:

```
let loop = 0.0213        # this card, period 512, measured with a cable
let ref = delay(tone, loop)
```

The rules, including the review's three fixes:

1. **The period must equal the engine's block, or the two deadlock.**
   The engine reads a whole `AITHER_BUFFER` block before it writes
   anything (the `while got < bytes` loop in `pumpPipe`). If `card`'s
   period is shorter, or not a multiple of the block, `card` waits for
   output that aither won't make until it gets more input. `card`
   starts the child, so it sets `AITHER_BUFFER` (its period) and
   `AITHER_RATE` (the card's rate) in the child's environment. Then
   the two can't disagree.
2. **It runs any command, and passes on what it plays.** A display can
   sit inside the loop just before the DAC (the `sh -c` line above).
   That is where the displays' heard-sample clock works: `stream_now`
   in `tools/display.h` checks how much the downstream reader has
   taken, using FIONREAD. `card` also writes what it plays to its own
   stdout, the way the displays note says `play` will: the input
   unchanged, never blocking, and dropping blocks to a slow reader
   rather than stalling the sound.
3. **On a capture xrun, feed the child zeros for the lost frames.**
   ALSA reports how many frames were lost. Re-priming playback keeps
   the loop delay right, and the zeros keep `t` equal to the card's
   frame count. `card` prints the wall-clock time of frame 0 to
   stderr, so `t` gives exact timestamps for logging (open question 4).

**Clocks.** The hardware in a chain is its clock. The displays already
behave this way: their reader stays within 1 % of the nominal rate and
never waits behind a real-time source (`tools/display.h:91`), so
`arecord | aither | scope` can't make `arecord` overrun. The displays
note's wording on this is stale. Its author is updating it when they
write the tv docs, so this note leaves it alone. Active sensing needs
one card for both directions. Two crystals drift, which a lock-in's
amplitude survives but its phase doesn't.

**Cost-variable patches.** Tail recursion (approved 2026-10-16, being
built) makes a sample's cost depend on the data. Under `card`'s hard
deadline per period, a slow burst becomes an xrun and `card` restores
the delay. Patches that use it inside a `card` loop need CPU headroom,
which matters on the uConsole with its fast cores off.

**Rejected:** duplex inside the engine. It went out with miniaudio on
purpose; the engine never touches hardware.

**Open:** `card` as its own tool or as a mode of `play` (separate is
leaner, since `play` stays a simple filter); and whether `card` should
also export the measured delay to the patch (it would need an engine
feature; writing it by hand needs none).

## As built (2026-10-17)

- **The engine did need one change.** Its pipe I/O went through stdio,
  which reads ahead on stdin: after the first block, the engine only
  answered every second block, and `card` deadlocked. `pumpPipe` now
  uses read(2) and write(2), and the engine is lockstep.
- Rate and period: `card` asks for `AITHER_RATE`, takes what the card
  can do (44100 on the es8388) and gives the command that rate and
  `AITHER_BUFFER=512`. 32-bit samples when the card has them.
- The xrun estimate (see rule 3) is from the clock, to whole periods.
  Tested by stalling a command for 0.3 s: one xrun, and its frame count
  stayed within about 3 ms of the wall clock afterwards.
- Ctrl-C goes to the command; `card` exits when the command does, with
  its status, and reports the xruns.
- Not yet measured: the loop delay with a cable. The capture on the
  uConsole read as zero in the first test, probably a muted capture
  mixer; `alsa-utils` (for `amixer`) isn't installed.
- The engine's "bye" on exit went to stdout, into the float stream.
  It goes to stderr now (2026-10-17).
- The uConsole's es8388 has no built-in mic. Its one analogue input is
  the mic contact on the headphone jack (Line 2), and with a headset
  plugged in it still reads a flat constant on every input route: the
  ADC or its data line isn't working on this board, not yet diagnosed.
  Real input needs a USB sound card, which stereo sensing needs anyway.
